# 하위 티켓 위임·리뷰와 병렬 병합 구현안

2026-11-22에 `997fb30`을 기준으로 작성한 구현 제안이다.

시니어가 할당받은 Git 티켓의 일부를 주니어에게 하위 티켓으로 발행한다. 주니어가 제출하면 시니어가 같은 워커 세션에서 리뷰하고, Q가 승인된 변경을 시니어의 작업 브랜치에 병합한다. 시니어는 합쳐진 결과를 검증하고 부모 티켓을 제출한다. Integrator는 최상위 결과를 프로젝트 브랜치에 병합한다. 원래 시니어 세션을 복구할 수 없으면 사용자가 지정한 서브에이전트로 부모 티켓을 인계할 수 있다.

## 현재 구현과 재사용 범위

- `ticket_create`는 `requested_member_id`로 후보를 지정할 수 있다. 발행 후 배정은 기존 Decisions 경로를 거친다. Library의 `ReviewAttempt`와 리뷰 알림은 현재 프로젝트 Integrator에 묶여 있다. [티켓 도구](../internal/workitemtools/tools.go#L86) · [리뷰와 알림](../workitems/coordinator.go#L552)
- Git worktree는 어느 단계에서든 직계 부모의 worktree를 기준으로 만들 수 있다. `gitwork.Prepare`가 대상 브랜치와 기준 커밋을 기록하며, 기존 병합 경로는 그 요청의 `RepositoryRoot`를 사용한다. 부모 worktree를 현재 실행의 실제 checkout으로 사용하도록 워커 시작 경로를 확장한다. [worktree 생성](../gitwork/manager.go#L44) · [티켓 워커](../app/coordinator.go#L203) · [병합 작업](../coordinator/engine.go#L368)
- Native 워커는 저장된 대화에 후속 턴을 붙이고, ACP 워커는 지원되는 연결에서 저장된 원격 세션을 재개한다. 기존 재시도는 멤버와 실행 정의가 일치할 때 `WorkerSessionID`와 `WorktreeID`를 이어 쓰며, 열린 worktree의 일반 재배정을 막는다. [Native·ACP 워커](../app/coordinator.go#L383) · [실행 예약](../workitems/coordinator.go#L295)
- 현재 Git 병합은 대상 HEAD가 티켓의 원래 기준 커밋과 같아야 한다. 두 작업이 같은 커밋에서 갈라지면, 첫 병합 후 다음 작업은 변경 파일이 달라도 `ErrBaseMoved`가 된다. 아래 병합 변경을 먼저 적용하면 `main`과 각 부모 브랜치에서 같은 방식으로 병렬 작업을 수용할 수 있다. [현재 병합 검증](../gitwork/manager.go#L214)

## 부모 관계와 리뷰 권한

`ticket_create`에 `as_child` 옵션을 추가한다. Q 호스트가 현재 워커의 실행 컨텍스트에서 부모 티켓을 결정한다. Library는 같은 프로젝트에 속한 활성 Git 실행인지, 위임이 허용된 세션인지 확인한다. 티켓 본문, `author`, 모델이 제시한 임의의 세션 ID와 Git 경로는 권한 판정에 사용하지 않는다.

| 저장할 항목 | 용도 |
| --- | --- |
| 부모 티켓 ID | 직계 부모 조회, 하위 작업 대기, 리뷰 전달 |
| 부모 worktree ID | 최초 위임 시 연결한 브랜치의 수명과 일치하는지 확인 |
| 발행 세션 및 요청 ID | 발행 이력과 동일 요청 재시도 시 중복 생성 방지 |
| 현재 리뷰 실행 | 부모 티켓의 활성 실행에서 결정. 리뷰 대상 하위 attempt와 제출 HEAD를 함께 확인 |

부모 관계와 하위 티켓은 같은 Library 트랜잭션에서 저장한다. 기본 티켓은 기존 생성·배정 경로를 사용한다. 초기 범위는 같은 프로젝트와 Git 저장소 안의 Git 티켓이다. 기존 멤버 설정의 실행 root는 후보 자격 판정에 쓰고, 실제 하위 checkout은 부모 worktree에서 파생한다. 여러 단계가 필요할 때도 각 티켓은 직계 부모만 기록한다.

하위 티켓의 `ticket_review`는 그 부모의 현재 리뷰 세션에만 허용한다. Library가 하위 티켓, 활성 attempt, 제출 HEAD와 리뷰어의 현재 실행 세대를 함께 검사한다. 수정 요청은 현재 피드백 경로를 사용해 주니어에게 돌아간다. Integrator의 자동 리뷰 알림은 최상위 티켓에 전달한다.

모델은 위임할 때 `requested_role`로 프로필 역할을 지정할 수 있다. Decisions가 프로젝트의 해당 역할 후보 중 작업자를 선택하고 Q가 배정된 멤버와 세션을 기록한다. 부모 워커와 Integrator의 자동 리뷰 턴에는 Q가 대상 attempt와 재시도 키를 도구에 전달한다. 모델은 읽기 도구를 호출하고 `ticket_review`에 결정과 피드백을 전달한다. Studio에서 특정 멤버를 선택하는 인계 경로도 유지한다.

`depends_on`은 실행 전제 조건으로 유지한다. 동일 부모 아래에서는 먼저 병합된 결과가 필요한 티켓이 앞선 형제 티켓에 의존할 수 있다. 하위 티켓의 `done`은 직계 부모에 반영됐다는 뜻이므로 프로젝트 브랜치에서 결과가 필요한 티켓은 최상위 티켓을 의존 대상으로 지정한다. 초기 구현에서 `depends_on`은 최상위끼리 또는 같은 부모 worktree를 공유하는 하위 티켓끼리 허용한다. 기존 순환 검사도 적용한다. [티켓 의존성](ticket-dependencies.md)

## 부모 세션의 대기와 재개

1. **발행과 실행 종료.** 시니어가 하위 티켓을 하나 이상 발행하고 현재 모델 턴을 끝낸다. Q는 시니어 대화와 실행 상태를 저장하고 부모 checkout이 깨끗한지 확인한다. 커밋되지 않은 수정분이 있으면 같은 세션에 정리할 내용을 알려주고, 정리가 끝날 때까지 하위 예약을 미룬다. 부모 Git 요청은 작업 중으로 보존한다. 기존 `Submit`은 변경이 없는 worktree를 정리할 수 있으므로 최종 제출 시점에 호출한다. [Git 제출과 정리](../gitwork/manager.go#L138)
2. **대기와 하위 실행.** Library가 부모를 하위 작업 대기 상태로 전환하면 부모는 실행 슬롯을 반환한다. 하위 티켓은 부모가 대기 상태에 들어간 뒤에만 예약할 수 있다. 같은 부모에서 출발한 하위 티켓도 정해진 프로젝트 용량 내에서 병렬 실행할 수 있다. 프로젝트 동시 실행 한도가 1이어도 하위 작업이 시작돼야 한다. [실행 슬롯 집계](../workitems/scheduling.go#L15)
3. **리뷰 턴.** 하위 attempt가 `awaiting_review`가 되면 Library가 지속되는 리뷰 이벤트를 만든다. Coordinator는 부모 티켓을 원래 멤버와 `WorkerSessionID`로 이어 실행한다. Native는 기존 후속 턴을 사용하고, ACP는 저장된 원격 세션 ID를 `session/resume` 또는 `session/load`에 전달한다. 일반 배정 모델 호출은 최초 배정과 신규 하위 티켓에 적용한다. [Native 후속 턴](../app/coordinator.go#L383) · [ACP 재개](../app/acp_client.go#L276)
4. **승인과 병합.** 시니어가 diff와 완료 기준을 확인하고 승인하면 하위 병합이 큐에 들어간다. 리뷰 턴은 부모 checkout을 읽기 용도로 사용한다. 부모 워커가 실행을 반환한 뒤 병합을 예약해, 리뷰 턴과 Git 적용이 같은 checkout에서 겹치지 않게 한다. 병합이 성공하면 Library가 하위 티켓을 `done`으로 기록한다.
5. **최종 검증과 제출.** 필요한 하위 티켓이 모두 `done`에 도달하면 병합 결과를 담은 별도 이벤트로 같은 부모 세션을 재개한다. 시니어는 합쳐진 상태에서 검증과 추가 수정을 마치고 부모 티켓을 제출한다. 다음 리뷰어는 부모의 직계 상위 실행 또는 최상위 티켓의 Integrator다.

한 부모 세션의 후속 턴은 순서대로 실행한다. 이벤트에는 하위 attempt ID와 단계에 묶인 안정적인 작업 ID를 붙여 중복 전달을 처리한다. 오래된 attempt의 리뷰 이벤트는 현재 하위 attempt와 대조한다. 하위 작업이 실패하거나 취소되면 부모에 티켓 링크와 대기 사유를 표시한다. 부모 취소가 접수되면 하위 작업의 새 예약·병합을 막고, 활성 하위 실행을 정리한 뒤 부모 worktree를 닫는다.

### 지정 멤버에게 인계

동일 세션을 우선 재개한다. 잠시 바쁜 세션은 재시도 대상으로 남기고, ACP 재개 미지원이나 체크포인트 손실처럼 복구할 수 없는 경우 Studio에 원인을 표시한다. 실행 결과가 불명확하면 먼저 이미 기록된 티켓·리뷰·Git 결과를 읽어 확인한다.

사용자가 프로젝트에 합류한 특정 서브에이전트를 골라 **부모 티켓 인계**를 요청할 수 있다. Library에서 인계 가능한 대기 상태와 현재 실행 세대를 확인하고 새 소유권을 기록한다. 새 워커 세션에 동일 부모 worktree와 미처리 하위 티켓 및 리뷰 증거를 전달한다. 이전 세션은 토큰과 실행 세대로 차단한다. 하위 티켓을 제출한 멤버는 그 결과의 리뷰어가 될 수 없다. 인계는 현재 worktree의 브랜치·저장소 식별을 재검증한 뒤 진행한다.

## 최신 대상 HEAD에 병합

같은 브랜치에서 일하는 여러 티켓은 동시에 분기하고 구현할 수 있다. 브랜치별 큐에서 대상 갱신만 순차로 적용한다. 프로젝트 브랜치와 하위 티켓의 부모 브랜치에 같은 규칙을 쓴다.

```text
분기   프로젝트 브랜치 → 시니어 worktree → 주니어 worktree
병합   프로젝트 브랜치 ← 시니어 최종 제출 ← 주니어 승인 결과

공통 기준 B에서 시작한 티켓 A와 B2가 모두 승인됨
대상 B   + 승인된 A의 HEAD  → 후보 M1 → 적용
대상 M1  + 승인된 B2의 HEAD → 후보 M2 → 적용
```

### 병합 후보와 반영

1. 큐에서 사용할 승인 기록의 기준 커밋 `B`와 제출 HEAD `H`를 확인한다. 대상 브랜치와 현재 HEAD `T`를 읽고, `T`가 `B`에서 정상적으로 전진했는지(`B`가 `T`의 조상인지) 확인한다. 대상 브랜치가 교체되거나 이력이 재작성됐으면 충돌 사유를 기록하고 재검토 대상으로 돌린다.
2. `git merge-tree --write-tree T H`로 병합 결과를 계산한다. 충돌이 없으면 첫 부모가 `T`, 둘째 부모가 승인된 `H`인 후보 커밋 `M`을 만든다. 승인된 `H`와 리뷰 당시 `B`는 그대로 보관한다. 프로젝트에 병합 검증 명령이 있다면 실제로 적용할 `M`을 격리된 checkout에서 검증한다.
3. Git의 임시 ref로 후보를 보존한 뒤 승인 ID, attempt, 실제 대상 `T`, 승인된 `H`, 후보 `M`을 Library에 영속화한다. 적용 직전 같은 저장소·대상 ref의 기존 병합 락 아래에서 승인과 실행 세대, 현재 대상 HEAD, checkout 상태를 다시 확인한다. `T`가 전진했으면 최신 HEAD에서 후보를 다시 만들고 필요한 검증을 다시 실행한다.
4. 깨끗한 대상 checkout에서 후보를 `git merge --ff-only M`으로 적용하고 Git 결과를 확인한 뒤 Library에 완료를 기록한다. 기존 병합에서 적용되는 Git 훅과 서명 설정의 기대 동작을 후보 생성·검증 경로에서 확인한다. 병합 후 불필요해진 하위 worktree와 임시 후보 참조는 기존 정리 흐름에 맞춰 제거한다.

### 충돌, 재시도와 복구

| 관측 결과 | 후속 동작 |
| --- | --- |
| 대상이 정상 전진함 | 최신 HEAD에서 같은 승인 커밋으로 후보를 다시 계산한다. 반복 경쟁으로 즉시 반영할 수 없으면 큐에 돌려보낸다. |
| Git 충돌 또는 검증 실패 | 대상 checkout을 보존하고 이 티켓만 보류한다. 파일과 실패 이유를 워커에게 전달하며, 큐는 다음 티켓을 진행한다. |
| 워커가 충돌을 해결해 재제출 | 최신 대상 커밋을 새 리뷰 기준으로 기록하고 변경된 HEAD와 diff의 승인을 다시 받는다. 이전 승인과 기준은 이력에 보관한다. |
| Git 적용 직후 종료 | 저장된 후보 `M`이 지정한 대상 브랜치 이력에 들어 있는지 확인한다. 이미 반영됐으면 결과 기록과 정리를 이어간다. 그 후 다른 티켓이 병합되어도 같은 후보를 식별할 수 있다. |
| 대상 checkout 변경이나 이력 재작성 | 브랜치 전환, dirty checkout, 진행 중인 Git 작업, 기준 커밋 유실을 구분해 보류 사유로 표시한다. |

병합 전후의 저장 순서는 기존 복구에서 일반화해야 하는 부분이다. 현재 복구는 대상 HEAD의 두 부모가 원래 기준 커밋과 제출 HEAD일 때만 이미 실행된 병합을 채택한다. 후보 SHA를 기록하면 실제 대상이 전진한 경우와 이미 더 뒤의 커밋까지 진행된 경우도 확인할 수 있다. [현재 복구 조건](../gitwork/manager.go#L234) · [병합 예약](../workitems/coordinator.go#L804)

## 적용 순서와 검증 기준

1. **최신 HEAD 병합부터 적용한다.** 현재 최상위 티켓 큐로 같은 기준점에서 시작한 두 작업을 모두 승인해 병합한다. 두 번째 적용 전 대상 전진, 충돌 후 다른 티켓 진행, 기존 승인 HEAD 변경, dirty checkout, Git 적용 후 Library 기록 전 종료를 검증한다. 저장소와 대상 브랜치 단위의 적용 락과 기존 완료·정리 경로를 재사용한다.
2. **하위 관계와 리뷰 전달을 연결한다.** Library에서 관계·대기를 저장하고, Q 워커가 부모 worktree에서 하위 분기를 만들도록 한다. 동시 실행 한도 1에서 부모가 대기하며 주니어가 실행되는지, 한도가 여러 개일 때 형제 작업이 동시에 실행되는지, 승인 결과가 직계 부모까지만 전파되는지 확인한다. Native와 재개 가능한 ACP에서 같은 세션으로 리뷰·최종 제출을 이어가는 경로를 검증한다.
3. **지정 멤버 인계와 Studio 표시를 추가한다.** 부모·하위 티켓 링크, 현재 리뷰어, 브랜치 병합 대상과 대기 이유를 티켓 상세에 표시한다. 인계 후 동일 worktree를 사용하고 이전 세션의 리뷰를 거부하는지, 재시작과 중복 이벤트로 하위 티켓이나 병합이 두 번 생성되지 않는지 확인한다.

기존 티켓은 부모 관계가 없는 최상위 티켓으로 읽는다. 상태 및 병합 기록의 변경에 맞춰 Library 카탈로그 마이그레이션과 프로토콜 호환성을 검증한다. 새 작업 상태를 처리할 수 있는 Studio·Library 조합에서 하위 발행을 허용한다.

## 조사에서 확인한 근거

- 기존 테스트에서 직계 부모 worktree를 거친 병합, Native 후속 실행에서의 워커 재사용, ACP 원격 세션 재개가 통과했다. [중첩 Git 병합](../gitwork/manager_test.go#L176) · [Native 워커](../app/coordinator_test.go#L64) · [ACP 워커](../app/coordinator_test.go#L235)
- 임시 Git 저장소에서 세 단계 worktree의 직계 병합, 동일 기준점에서 출발한 형제의 `ErrBaseMoved`, 최신 대상에서 후보를 다시 계산한 뒤 연속 병합을 확인했다. 후보 계산 중 충돌이 대상 checkout에 남지 않고, 적용 뒤 대상이 더 전진해도 후보 커밋을 이력에서 식별할 수 있었다. 이 결과는 Git 동작의 검증 근거다. Library 상태 전이와 Studio의 전체 흐름은 위 구현 단계의 통합 테스트에서 검증한다.

### 구현 시 확인한 제약

전진한 대상과 병합 후보를 계산하려면 `merge-tree --write-tree`를 지원하는 Git이 필요하다. Git 병합 커밋 훅이 설정된 저장소는 훅을 실행하는 기존 경로를 사용한다. 이런 저장소에서 대상이 전진하면 워커가 새 기준을 반영하고 다시 리뷰를 받는다. 프로젝트별 병합 후보 테스트 명령을 실행하는 설정은 후속 작업이다. [현재 사용 가이드](library.md)
