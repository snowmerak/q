# web_search 도구 연결 및 검증

2026-10-13, Q의 MCP stdio 서버와 in-process Runtime에 `web_search`를 등록했다.
기존 공개 AgentLoop를 통해 호출되며, 결과는 일반 도구와 같은 Loom 경로에 저장된다.
독립적인 범용 AgentLoop를 추가하지 않았다.

## 역할 경계

- Gemma4 E4B / System One: 다음 링크·근거 구절 선택, 브라우저 관찰, 검색 입력 여부와 기존 입력값 선택, 검색 제출, 출처 판정, `finish` 시도 선택.
- Qwen3.8 27B / System One: 수집된 근거로 요구사항 각각과 원래 목표의 완료 여부를 `supported`/`missing`으로 판정. 단계 예산 끝의 완료 검사에도 적용.
- 호출한 에이전트의 모델 / 생성형 호출: System One이 요청한 새 검색어 작성 또는 원래 목표의 요구사항 분해. 탐색·최종 답변은 담당하지 않는다. 아래 과거 실험에서는 Qwen을 사용했다.
- Go: HTTP/HTML 추출, URL 정리·중복 제거, 검색 결과 페이지와 본문 구분, 지정 도메인 필터, 일부 알려진 검색 챌린지 감지, 메뉴·본문 크기 제한, 참조 갱신·현재 폼 재검사, 이력 관리, 시간·호출 예산, 브라우저 정리.

현재는 global `systemone.json`에 `role_models.web_search`와
`role_models.web_search_finish`를 모두 명시해야 검색 도구가 노출된다.
Studio Settings → System One에서 탐색·완료 모델을 각각 설정할 수 있다.
검색어 생성은 호출한 에이전트의 기존 클라이언트·모델·reasoning 설정을 재사용한다.
별도 provider 직결, Qwen 기본값, `websearch.json` override는 제거했다.
메인 루프는 현재 선택 모델, 서브에이전트는 역할별 선택 모델을 전달하며,
MCP 경계를 지나거나 병렬 호출해도 각각의 설정을 유지한다.
결과의 `coverage_model`과 `coverage_calls`로 완료 검사 모델/호출 횟수를 확인한다.
`system_one_calls`는 완료 검사를 포함한 전체 native 호출이며 `planner_calls`는
검색어 작성·요구사항 분해의 생성형 호출만 센다.

처음 검색어가 없으면 목표를 그대로 검색하므로 시작에 생성형 호출이 필수인 것은 아니다.
검색 필드에는 현재 검색어나 이미 있는 요구사항을 입력한다. 새로운 문자열을 만들려면
호출 모델의 `query` 또는 `decompose`를 거친다. 입력·제출 대상은 구조적으로 식별한 검색
컨트롤이며, GET 폼 또는 독립 검색 입력에 제한한다. 페이지 JS 자체를 막는 네트워크
샌드박스는 아니다. iframe/shadow DOM, 로그인, 업로드, 임의 폼 조작은 지원하지 않는다.

정적 문서는 Go HTTP로 읽는다. 렌더링/조작이 필요하면 설치된 Chrome/Chromium을
별도 임시 프로필로 실행한다. 검색마다 브라우저를 소유하고 반환·오류·취소 시 닫는다.
모델 응답을 기다리는 동안 탭이 만료되지 않도록 검색 세션의 유휴 기한은 전체 호출
기한보다 길다. Docker나 상주 브라우저 서비스는 필요 없다.

## 실제 OEV 호출에서 드러난 문제

아래 결과들은 완료 검사 모델을 Qwen으로 분리하기 전 Gemma로 실행한 기록이다.
개선 중의 스모크 호출이며, 반복 측정이나 완료율 벤치마크가 아니다.
전체 원본 MCP 결과를 `docs/experiments/web-search-tool-*-result.json`에 보존했다.
스모크 실행의 임시 Loom 저장소는 제거되므로 저장된 receipt의 Loom 참조는 일시적이다.

| 호출 | System One | Qwen | 관찰 |
|---|---:|---:|---|
| 검색 v1 | 12 | 0 | 근거 없이 완료를 반복 선택. 결과는 미완료. 근거가 없을 때 완료 후보를 제거하도록 수정 |
| 검색 v2 | 14 | 2 | 실제 링크 탐색과 검색어 재작성 동작 확인. 미러와 블로그 탐색 후 미완료. 지정 도메인 밖의 링크 후보 제거 및 세션 유휴 기한 수정 |
| 공식 문서 직접 시작 v1 | 3 | 0 | 원문 근거 1개 수집 후 System One 타임아웃. 부분 결과 반환. 다른 실제 호출과 겹친 시점이므로 원인을 서버 부하로 단정할 수 없음 |
| 검색 v3 | 14 | 0 | 공식 페이지에서 근거 3개 수집했으나 두 페이지를 왕복. 미완료. 뒤로가기가 이력 스택을 소비하도록 수정 |
| 공식 문서 직접 시작 v2 | 10 | 0 | 완료. 원문 근거 8개를 수집한 뒤 예산 경계의 독립 완료 검사 통과. 첫 두 구절에 자원 정리와 작업 종료를 기다리지 않는다는 설명이 포함됨 |
| 검색 v4 | 15 | 1 | 왕복 반복·탭 만료 없이 공식 문서까지 탐색하고 근거 5개 수집. 12단계에서 미완료. 실제 원문에는 두 답의 근거가 있었지만 완료 검사는 자원 정리 이유를 미지원으로 판정 |

완료 검사는 요구사항 각각과 원래 목표를 함께 확인한다. 분해가 일부 목표를 빠뜨려도
원래 목표 검사가 남는다. 완료 검사에 실패한 뒤에는 새 근거가 모여야 재검사를
선택할 수 있으며, 같은 근거를 예산 끝에서 다시 판정해 결과를 뒤집지 않는다.
이 역시 모델 판단이므로 미묘한 조건·예외를 완벽히 검증한다는 의미는 아니다.
공식 문서 직접 시작 v2에서는 실제 답변 근거를 생성형 호출 없이 확보했지만,
필요 이상으로 구절을 모았다. 조기 종료와 검색 목적지 선택의 효율은 개선 여지가 있다.
검색 v4는 완료 검사에도 false negative가 생길 수 있음을 보여준다. 같은 문서라도
수집한 주변 구절과 상태에 따라 판단이 달라졌다. 따라서 현재 `status`는 최종 진실
판정이 아니며, 원문 근거와 미해결 목록을 함께 검토해야 한다. 완료 검사를 Qwen으로
분리한 뒤에도 상태 표현·문항·후보 구성과 실제 판정 정확도를 확인해야 한다.

## 완료 검사 모델 분리 후 실제 호출

`web-search-tool-go-document-qwen-finish-result.json`은 같은 공식 문서에서 시작한
실제 MCP 실행이다. 탐색·출처는 Gemma4 E4B가 맡았고 근거 8개를 수집했다.
완료 검사는 `qwen3.8-27b`로 1회 호출했으며 생성형 planner 호출은 0회였다.
총 native 호출 10회 중 9회는 Gemma, 1회는 Qwen이다. Qwen 완료 검사는
60초 제한에서 타임아웃되어 근거를 보존한 미완료 결과를 반환했다.
모델 분리의 라우팅은 확인했지만 이 호출로 판정 정확도 개선을 확인하지는 못했다.

첫 두 근거만 넣은 동일 완료 문항의 native 재실행은 약 40.65초에 응답했다.
요구사항별로 자원 정리 이유는 `missing`, 작업 종료를 기다리는지는 `supported`,
원래 목표 전체는 `supported`로 판정했다. 자원 정리 이유의 원문 근거가 있으므로
false negative와 개별/전체 판정 간 불일치가 남아 있다. 완료는 모든 문항이
`supported`여야 하므로 이 응답으로도 완료 처리하지 않는다. 요청·응답은
`web-search-qwen-finish-small-request.json`과 `web-search-qwen-finish-small-result.json`에
보존했다. 이는 근거를 줄인 별도 native 호출이며 전체 MCP 실행의 성공 결과가 아니다.

## 완료 검사 시간 제한 조정

사용자 요청에 따라 native 완료 검사 제한을 60초에서 30분으로 늘렸다.
완료 전용 HTTP 클라이언트는 30분 5초, 전체 검색은 35분, 검색 브라우저의
유휴 기한과 스모크 실행은 36분으로 맞췄다. 탐색·출처 판단은 기존 1분,
검색어 작성·분해는 기존 90초를 유지한다. 호출자의 더 짧은 deadline과 취소는
계속 적용된다. 근거 수·문항·모델·입력은 변경하지 않고 공식 문서 입력을 재실행했다.

재실행은 **완료**됐다. 이전 60초 제한 실행과 수집한 8개 근거의 URL·제목·본문이
완전히 동일함을 JSON 비교로 확인했다. 원래 목표와 두 요구사항을 모두 지원으로
판정했고 미해결 요구사항과 오류는 없었다. 탐색·출처 Gemma native 호출 9회,
Qwen 완료 native 호출 1회, 생성형 planner 호출 0회였다.

스모크 드라이버의 전체 벽시계 시간은 **225.585초(약 3분 46초)**였다.
이는 `go run` 빌드·웹 읽기·Gemma 탐색·Qwen 검사 전체를 포함하며 Qwen만의
응답 시간은 별도로 측정하지 않았다. 기존 60초 타임아웃을 모델의 판정 실패나
성능 열세로 해석한 것은 성급했다. 이번 동일 입력의 완료는 확인했지만 반복 측정이나
다른 과제의 정확도 개선을 입증한 결과는 아니다. 두 구절 재실행에서 관찰한
개별/전체 판정 불일치도 별개의 관찰로 남는다.

- 결과: `web-search-tool-go-document-qwen-finish-30m-result.json`
- 시간 기록: `web-search-tool-go-document-qwen-finish-30m-timing.json`

시간 제한 변경 후 전체 Go 테스트, vet, 빌드, 변경 패키지 lint, govulncheck가
통과했다. 완료 판단에 30분 deadline이 전달되고 탐색 판단은 1분을 유지하는
테스트도 통과했다.

## 검색 v4의 고정 근거로 완료 모델 비교

`scripts/websearchsmoke/compare-coverage.ps1`은 실제 검색 v4의 최종 근거 5개를
그대로 재사용한다. 새로운 검색·근거 수집·생성형 호출은 수행하지 않는다.
production 완료 검사의 지시문·선택지·두 요구사항·원래 목표를 그대로 사용하며,
모델만 `gemma4-e4b`와 `qwen3.8-27b`로 바꾼다. 각 모델을 3회씩 순차 호출하고
라운드마다 호출 순서를 바꾸며, 두 모델 모두 native 요청 제한은 30분이다.
중간 결과와 원본 요청·응답·호출 시간을 매 호출 전후 JSON으로 저장한다.

사전에 확인한 기대 판정은 세 문항 모두 `supported`다. 네 번째 근거의
공식 context 문서는 CancelFunc 호출이 자식 컨텍스트·부모의 참조·타이머를
정리하고, 누락 시 누수가 생긴다고 명시한다. 다섯 번째 근거는 작업 종료를
기다리지 않는다고 명시한다. 따라서 두 요구사항과 두 조건을 함께 묻는 원래
목표 모두 원문 근거로 답할 수 있다. 이 기대값은 모델 응답을 보고 바꾸지 않는다.

```powershell
& ./scripts/websearchsmoke/compare-coverage.ps1 `
  -Receipt docs/experiments/web-search-tool-go-v4-result.json `
  -InputFile docs/experiments/web-search-tool-go-input.json `
  -Output docs/experiments/web-search-v4-coverage-model-comparison.json `
  -Repeats 3 -TimeoutSeconds 1800
```

이는 한 과제의 동일 입력에 대한 반복 비교이며 범용 검색 정확도나 모델 전반의
속도 우위를 입증하는 벤치마크는 아니다.

### 실제 비교 결과

2026-10-13, 총 6회 native 호출이 모두 정상 응답했다. 저장된 6개 요청을
JSON 비교하여 모델 이름을 제외한 상태·근거·문항·선택지가 완전히 동일함을
확인했다. 생성형 출력 토큰은 모든 호출에서 0이었다.

| 완료 문항 | 기대 판정 | Gemma4 E4B, 3회 모두 | Qwen3.8 27B, 3회 모두 |
|---|---|---|---|
| CancelFunc를 호출해야 하는 이유 | supported | missing | supported |
| 호출이 작업 종료를 기다리는지 | supported | supported | supported |
| 원래 목표 전체 | supported | missing | supported |

Gemma는 이전 검색 v4의 false negative를 그대로 재현했다. Qwen은 세 문항을
모두 올바르게 판정해 이 동일 근거에서 완료 검사를 통과했다. **이 사례의 완료
판정 정확도 개선은 확인했다.** 탐색이나 입력 처리의 개선을 측정한 것은 아니다.

첫 비교 호출은 Qwen 54.04초, Gemma 10.44초였다. 후속 호출은 Qwen 1.01/1.14초,
Gemma 0.59/0.35초였으나 native usage가 대부분의 입력 토큰을 cached_tokens로
보고했으므로 캐시 영향을 받는 반복 시간이다. 첫 호출도 일부 입력 캐시가 있었고,
모델의 보편적 속도 비교나 독립 과제의 정확도 표본으로 해석하지 않는다.

원본 요청·응답·확률·usage·시간은
`docs/experiments/web-search-v4-coverage-model-comparison.json`에 보존했다.

## 검증

일반 테스트는 실제 유료 모델을 호출하지 않는다. 가짜 native System One/Chat endpoint와
로컬 HTTP 서버, 설치된 실제 브라우저로 다음을 확인했다.

- System One의 입력·제출 흐름에서 Qwen 호출 0회, 입력 뒤 새 참조 사용.
- 미완료 검사 뒤 `query` 요청 시에만 planner 호출, `decompose`가 원래 목표를 대체하지 않음.
- 비밀번호/POST 검색 폼 제외, 스냅샷 뒤 GET→POST 변경 시 제출 거부, 제출 이후 관찰 대기.
- 잘못된 선택, 시간·단계 예산, 취소, planner 오류에서 부분 결과와 자원 정리.
- 도메인 접미사 위장 거부, 검색 리다이렉트 정리, CAPTCHA 감지에서 모델 호출 생략.
- native `web_search` 모델 역할 적용, planner 설정의 지연 로딩, ambient API key 전달 방지.
- `web_search_finish`의 별도 native 모델/provider 사용, 일반 탐색·출처 검사에 영향 없음.
- 명시적 finish와 예산 경계에서 모두 완료 전용 모델 사용, 완료 모델 오류 시 부분 근거 보존.
- 실제 MCP 호출·Loom 저장과 `package app_test`에서 공개 AgentLoop의 도구 광고·실행·결과 수신.

전체 Go 테스트, vet, 새 코드 대상 lint, 빌드, 취약점 검사, 모듈 아카이브 설치 검사를 수행했다.
실제 검색 경로에서 미완료 사례가 있었으므로 범용 웹 검색의 안정성이나 속도 우위를
확인했다고 주장하지 않는다. 실행 방법과 도구 인자는 `tools/README.md`에 있다.
