# Q 티켓 실행에서 사용자 결정을 받는 시점

2026-11-24 기준. Q 소스 `3e255f2`와 공개 프로토콜·SDK 문서를 바탕으로 검토했다. 관련 기능과 재현 작업은 [티켓 실행 워크플로우 백로그](ticket-workflow-backlog.md)에 있다.

## 권장 흐름

**모든 티켓에 짧은 시작 점검을 두고, 사용자 판단이 필요한 작업만 멈춘다.** 코디네이터는 목적, 허용 범위, 완료 기준을 이슈와 티켓에 남긴다. 티켓을 맡은 워커는 실행 초반에 선행 결과와 현재 상태를 보면서 결정이 필요한지 확인한다. 프로젝트가 명시적으로 요구하면 시작 승인을 걸 수 있고, 평소에는 사용자 요청 범위 안에서 실행한다.

| 방식 | 적합한 경우 | Q에서의 비용 |
| --- | --- | --- |
| 티켓마다 시작 승인 | 모든 작업의 개시를 사람이 통제해야 하는 프로젝트 | 자식·반복 티켓까지 승인 요청이 쌓인다. 승인 시점에 판단 근거가 부족할 수 있다. |
| 이슈 단위로 계획 승인 | 변경 범위나 운영 정책을 한꺼번에 합의할 때 | 승인 한 번으로 좁은 티켓 여러 개를 실행할 수 있다. 시작 후 발견되는 새로운 범위에는 별도 결정이 필요하다. |
| 시작 점검과 조건부 승인 | 워커가 초반에 근거를 확인하고 대부분의 작업은 무인으로 진행할 때 | 질문이 걸린 작업만 멈출 수 있다. 서버가 대기·재개를 저장하고, 통제 가능한 작업의 승인 경계를 집행해야 한다. |

티켓을 자르는 기준은 **독립적으로 검증할 결과, Git 수정 경계, 사용자 결정 시점**이다. 입력이나 결과를 소비하는 티켓에만 `depends_on`을 건다. 예를 들어 설정 이름을 바꾸는 워커가 초반에 예전 이름을 쓰는 외부 호출자를 발견하면, 기존 이름을 언제까지 지원할지 묻고 이름 변경만 대기시킨다. 영향을 받지 않는 사용량 화면 수정은 계속한다. 배포 결정에 개발과 검증 결과가 모두 필요하다면, 배포를 별도 티켓으로 잘라 해당 티켓 시작 시점에 배포 대상과 검증 결과를 보여준다. 사용자 요청과 프로젝트 정책에 배포가 포함돼 있다면 그 근거를 사용한다.

## Q에서 이미 쓸 수 있는 기반

- 코디네이터 프롬프트에는 사용자 인터뷰, 관찰 가능한 `acceptance`, 독립 결과 단위, 다중 `depends_on`이 이미 있다. 일반 실행 티켓은 생성 트랜잭션에서 `queued`가 된다. `ClaimTicket`은 예약 시점에 선행 티켓을 다시 검사하고 티켓·본문 리비전을 실행 기록에 남긴다. [코디네이터 프롬프트](../coordinator/coordinator_prompt.txt) · [티켓 생성](../workitems/items.go#L391) · [예약 및 선행 검사](../workitems/coordinator.go#L331)
- 실행 후 승인·변경 요청·거절은 기존 리뷰가 처리하고, 대기 중인 부모 티켓은 자식 결과를 받은 뒤 기존 워커 세션으로 이어갈 수 있다. 이 흐름은 사람 응답을 기다리는 티켓의 유사 사례다. 지금의 매니저 인박스는 리뷰 전달용이고, Studio의 워커 대화 화면은 조회용이다. - 일반 세션의 `ask_to_user`에는 질문 UI와 답변 경로가 있다. 일반 위임도 안전한 실행 경계에서 사용자 지시를 반영하는 `RunControl`을 넘긴다. 네이티브 티켓 워커는 체크포인트와 복구 경로를 쓰고, 현재 `RunControl`을 연결하지 않는다. 일반 질문 화면의 표시 요소를 재사용할 수 있고, 티켓 응답의 저장·재개는 티켓 런타임이 소유해야 한다. ## 프롬프트와 런타임의 역할

| 위치 | 책임 |
| --- | --- |
| 코디네이터 | 이슈에 사용자 목적, 범위와 제외 범위, 승인 근거, 미결정을 기록한다. 티켓에 소비할 입력·리비전, 결과물 한 개, 검증 방법, 결정을 받아야 하는 조건을 남긴다. 어떤 조사까지 허용됐는지도 명확히 한다. |
| 티켓 시작부 | 의존 결과와 기준 리비전을 확인한다. 먼저 읽기 위주로 근거를 모아, 사용자 판단이 필요하면 그 결정이 영향을 미치는 변경 전에 요청한다. 요구와 일치하고 되돌리기 쉬운 세부사항은 가정을 기록하고 진행한다. |
| Q 런타임 | 시작 승인, 질문 대기, 재개, 결과 리뷰를 별도 상태로 다룬다. 명시적 승인이 필요한 Q 관리 작업은 검증된 사용자 응답을 조건으로 실행한다. 인박스와 알림은 저장된 요청을 표시하고 답변을 해당 실행으로 전달한다. |

티켓 시작 점검은 역할 이름에 관계없이 공통으로 적용한다. 정해진 리비전과 정책을 비교하는 점검은 코드에서 수행하고, 판단에 필요한 읽기 위주 조사가 있을 때만 워커에게 맡긴다. 네이티브 워커의 `task_start`는 기존 시작 지점이고, ACP에도 적용할 승인 경계는 변경 권한을 가진 워커에 프롬프트를 보내기 전 Q 호스트에 둔다. 일반 채팅의 질문 카드 UI는 재사용할 수 있다. 응답은 해당 티켓, 시도, 워커 세션, 요청에 귀속시킨다.

### 프롬프트에 넣을 규칙

1. 이미 답한 요구나 승인한 범위를 다시 묻지 않는다. 사용자 결정은 외부에 드러나는 결과, 호환성, 허용 범위, 되돌리기 어려운 행위가 실질적으로 달라질 때 요청한다.
2. 배정 전에도 안전한 조사 범위를 정할 수 없다면 코디네이터가 먼저 확인한다. 근거가 티켓을 열어야 나오는 경우에는 티켓 시작부에서 확인한다. 필요한 근거를 얻는 조사가 크거나 다른 작업이 그 결과를 함께 쓰면 조사 티켓으로 분리한다.
3. 질문에는 결정 한 가지, 추천안과 이유, 다른 선택을 했을 때 달라지는 결과, 응답이 없을 때 영향을 받는 작업을 넣는다. 검증 로그·스크린샷은 근거로 링크하고, 긴 작업 중간 로그는 워커 타임라인에서 볼 수 있게 한다.
4. 실행 전에 확인할 수 있던 질문은 늦게 올리지 않는다. 실행 뒤에만 확인할 수 있던 조건이 결과를 바꾼다면 근거를 기록하고 압축을 마친 뒤 질문한다. 이미 승인한 범위를 벗어나는 변경은 결정이 확정될 때까지 보류한다.

### 기다리는 동안 실행이 어떻게 되는가

- **무인 기본 동작.** 승인된 범위와 정책 내에서 독립 티켓은 계속 실행한다. 답변 없이는 진행할 수 없는 티켓은 체크포인트를 저장하고 실행 슬롯을 반환한다. 그 결과를 필요로 하는 티켓만 `depends_on`으로 계속 대기한다. 답변을 생략할 수 있는 경우에는 사전에 허용된 기본값을 적용하고 기록한다.
- **응답과 재개.** 승인 범위는 영향을 받는 작업의 리비전과 연결한다. 배포처럼 실제 대상이 중요한 경우에는 배포할 커밋이나 산출물도 연결한다. 워커는 요청을 제안하고, 서버는 사용자의 인증된 응답을 받는다. 서버가 요청 ID와 현재 시도, 권한, 범위를 비교하고 요청을 한 번만 소비한다. 대기 중 작업 범위나 대상이 바뀌면 이전 결정을 다시 적용할 수 있는지 확인하고, 달라진 행동에는 새 결정을 받는다. 동일 워커 세션과 워크트리로 이어가는 것을 우선한다.
- **승인으로 보호할 작업.** 첫 버전에서는 Q가 실행하는 배포·외부 변경처럼 대상과 파라미터를 알고 있는 경계를 선택한다. 외부 ACP가 직접 실행하는 도구는 호출을 Q에 위임하는 범위에서 제어할 수 있다. 일반 셸이나 외부 에이전트에 이미 제공된 권한까지 보장하려면 실행 환경에서 권한도 제한해야 한다. ACP의 질문 전송과 세션 복구는 각각 기능 지원을 확인한다. [ACP 도구 호출](https://agentclientprotocol.com/protocol/v1/tool-calls) · [질문 전송](https://agentclientprotocol.com/protocol/v1/elicitation) · [세션 복구](https://agentclientprotocol.com/protocol/v1/session-setup)

### 뒤늦게 질문해야 한다면

1. 새 변경을 멈추고 진행 상태를 저장한다. 질문에 필요한 이슈·티켓 버전, 변경과 검증 근거, 이미 승인된 사항, 남은 선택을 구조화해 남긴다. 외부 호출의 결과가 불명확하면 다시 실행하기 전에 실제 상태를 확인한다.
2. 도구 호출이 끝난 경계에서 워커 컨텍스트를 압축하고 새 체크포인트를 저장한다. 압축할 분량이 없는 짧은 세션은 현재 상태를 체크포인트로 쓴다. 실제 이력과 승인 기록은 계속 조회할 수 있게 한다.
3. 성공한 체크포인트를 가리키는 질문을 인박스에 게시한다. 응답이 오면 같은 워커 세션에서 그 결정을 포함한 다음 턴을 시작한다. 압축이 실패하면 이전 체크포인트를 보존하고 압축을 재시도할 수 있게 한다. 인박스에는 질문 내용이 준비 중이라는 상태와 실패 이유를 표시한다.

네이티브 티켓의 자동 압축은 도구 라운드 사이에서 동작하고, 이미 실패 시 이력을 보존하는 테스트가 있다. 이 경로를 활용하는 명시적 체크포인트가 필요하다. 외부 ACP는 자체 문맥을 관리한다. Q가 확인 가능한 압축 이벤트나 에이전트별 제어 기능을 지원할 때만 원래 워커의 압축을 확인할 수 있다. 지원이 없다면 Q가 만든 인계 요약을 사용한 후속 티켓을 대안으로 삼고, 화면에도 인계 요약을 사용했다고 표시한다. [네이티브 압축](../subagent/delegation.go#L756) · [ACP 압축 이벤트](https://agentclientprotocol.com/protocol/v1/prompt-turn#session-compaction)

ACP 구현에서는 워커의 결과를 먼저 보존한 뒤, 해당 세션이 광고한 `/compact`를 별도 턴으로 호출한다. 같은 세션에서 새 압축 완료 이벤트를 받거나 Q ACP 서버의 체크포인트 응답을 받으면 이를 저장하고 질문을 게시한다. 실패한 시도는 인박스에 원인을 표시한다. 재시도는 원래 워커의 세션과 질문 초안을 이어받아 압축부터 진행한다. ## 외부 사례에서 적용할 부분

- GitHub Actions는 특정 배포 잡에 리뷰를 걸고, 승인 등 보호 규칙이 통과하면 해당 잡에 필요한 환경 비밀을 내준다. Q에서도 승인 단위를 전체 프로젝트 실행에서 배포나 외부 상태 변경처럼 실제로 결정해야 하는 작업까지 좁힐 수 있다. [GitHub 배포 리뷰](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments)
- OpenAI Agents SDK는 개별 도구 호출의 승인 조건을 평가하고, 승인 요청과 실행 상태를 저장해 나중에 재개할 수 있게 한다. Q가 빌릴 부분은 사용자의 응답을 정확한 실행 요청에 연결하는 방식이다. [OpenAI Agents SDK의 승인 및 재개](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)
- LangGraph는 중단 지점을 체크포인트에 저장하고, 재개 과정에서 일부 실행이 반복될 수 있어 외부 변경을 분리하거나 중복에 안전하게 처리하라고 안내한다. Temporal의 Workflow Update는 입력을 검증하고 받아들인 결정을 실행 이력에 기록한다. Q에서는 기존 티켓 저장소와 워커 체크포인트를 활용해 같은 원칙을 적용할 수 있다. [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) · [Temporal Workflow 메시지](https://docs.temporal.io/develop/go/workflows/message-passing)

## 구현 순서와 확인할 동작

1. **코디네이터 프롬프트와 시작 점검.** 우선 기존 이슈·티켓 본문과 `acceptance`를 활용해 선행 결과, 결정 시점, 검증 가능한 결과물의 예시를 추가한다. 새 워크플로 엔진이나 빌트인 역할을 요구하지 않는다. 승인된 로컬 수정, 조사 뒤 선택이 필요한 작업, 별도 배포 티켓을 더미 프로젝트에서 비교한다.
2. **인박스와 티켓 대기·재개.** 먼저 호스트가 원래 세션을 보존할 수 있는 네이티브 경로를 검증한다. 두 티켓을 병렬 실행해 한쪽 대기가 실행 슬롯을 막지 않는지, 재시작과 중복 응답에도 한 번만 재개되는지, 늦은 질문은 저장된 압축 뒤에만 게시되는지 확인한다. 지원되는 ACP는 같은 인터페이스로 이어 붙인다.
3. **명시적 시작 승인 정책.** 티켓 또는 프로젝트가 요구할 때만 켠다. 대기 중인 티켓은 기본 큐·재시도·예약 실행·자식 티켓 경로로도 승인 전 본작업을 시작할 수 없어야 한다. 결과 리뷰와 승인 후 기준 변경도 함께 확인한다.

### 40초 넘는 압축 중단

현재 데스크탑 프록시에서 일반 응답 헤더 대기는 40초, 수동 압축 `POST /api/v1/sessions/{session}/compact`는 5분이다. Studio 수동 압축은 여전히 HTTP 요청이 살아 있는 동안 실행된다. 이 설계만으로 사용자가 본 40초 전후 중단의 원인을 특정할 수 없다. 수동·자동 압축 각각에서 느린 모델 응답을 만들어 요청 ID, 프록시 경로, 모델 호출 시간, 체크포인트 저장 여부를 맞춰 보는 것이 다음 확인이다. 티켓의 늦은 질문에 쓰는 압축은 장시간 열린 브라우저 요청과 분리하는 편이 적합하다.
