# 커스텀 서브에이전트 설계 및 구현 계획

작성일: 2026-09-05

상태: 2026-09-05 구현 반영. 아래 설계의 Role 확장, 프로필 저장·실행,
`/model`의 Role 관리, TUI 생성·수정·삭제와 ACP 조회·실행 경로를 구현했다. 모델 실행 검증은
fake client 기반 테스트로 수행하며 실제 provider 연결 검증은 별도다.

## 1. 목표와 범위

사용자가 시스템 프롬프트, 제공할 도구 목록, 실행 Role을 지정해 Q 내부에서
동작하는 커스텀 서브에이전트 프로필을 만들고 TUI와 ACP에서 실행하게 한다.
필요하면 모델 설정을 담는 Role 이름도 사용자가 추가한다.

이번 구현은 기존 `/debug`, `/plan`, `/review`와 각 전용 Runner를 재구성하지
않는다. 내장 워크플로의 역할 배치, 도구 구성, 승인, 완료 계약은 그대로 둔다.
기존 기반 코드를 재사용하되 커스텀 실행 경로를 별도로 추가한다.

포함하는 기능:

- 사용자 정의 native Role 등록과 모델 설정 해석.
- 프로필 작성, 조회, 검증, 실행.
- `/model`에서 커스텀 Role을 생성·삭제하고 `/subagents`에서 프로필 생성·수정·삭제.
- TUI와 ACP의 동일한 목록·상세 조회 및 실행 결과.
- 기존 진행 이벤트, 취소, 컨텍스트 관리, 실행 기록 기반의 재사용.

포함하지 않는 기능:

- 사용자 정의 워크플로, 단계 연결, 분기, 승인 및 재시도 DSL.
- 새 권한 체계, 권한 상속, 샌드박스 또는 승인 정책.
- 외부 ACP 에이전트 프로세스 생성 및 연결 방식 변경.
- 프로필 간 위임, 재귀 실행, 일반 채팅 모델의 자동 프로필 선택.
- 기존 내장 기능을 프로필로 변환하거나 대체하는 작업.
- 실행 중단 지점 복구, 별도 headless CLI, ACP를 통한 생성·수정·삭제 UI.

## 2. 현재 코드와 연결 지점

| 위치 | 현재 역할 | 이번 변경 |
| --- | --- | --- |
| `config/config.go` | `agents.roles`, 모델 그룹, 내장 Role 검증 | 등록된 사용자 정의 native Role을 해석하도록 확장 |
| `subagent/spec.go` | Role을 실제 모델 후보·추론 설정·컨텍스트 한도로 해석 | 기존 `Resolve` 경로 재사용 |
| `subagent/context.go`, `lifecycle.go`, `progress.go`, `trace.go` | 컨텍스트 및 실행 관측 기반 | 새 Runner에서 재사용 |
| `app/slash_commands.go`, `app/model.go` | TUI 명령 등록과 실행 진입 | 커스텀 명령 추가 |
| `app/acp.go`, `app/acp_commands.go` | ACP 명령과 세션 실행 | 같은 커스텀 실행 서비스에 연결 |
| `app/agents.go` | 외부 ACP 연결 관리 | 기존 의미 유지 |

현재 `AgentsConfig.Roles`는 map이지만 `IsAgentRole`과 `EffectiveAgent`는
고정된 내장 이름을 검사한다. 따라서 YAML에 이름만 추가해서는 실행할 수 없다.
기존 Runner도 각자 특정 Role을 검사하므로 커스텀 프로필을 기존 Runner에
억지로 연결하지 않는다.

## 3. Role과 프로필

### Role: 모델 선택 설정

Role은 모델 또는 모델 그룹, 추론 강도 등 기존 `AgentConfig`의 native 모델
설정을 나타낸다. 작업 지침이나 도구 목록은 Role에 넣지 않는다.

global 설정 `~/.q/config.yaml`의 기존 `agents.roles`를 확장한다.

```yaml
agents:
  roles:
    analyst:
      model: my-analysis-model
      reasoning_effort: high
    quick-reader:
      group: lightweight
```

예제의 모델 ID와 그룹 이름은 사용 환경에 존재하는 값으로 바꿔야 한다.
모델과 그룹의 상호 배타성, 모델 목록 검증, 후보별 추론 설정 및 fallback
동작은 기존 규칙을 따른다. 둘 다 생략하면 기존처럼 활성 채팅 모델을 상속한다.

- 내장 native Role도 프로필에서 참조할 수 있다.
- 사용자 정의 Role은 `agents.roles`에 명시적으로 등록해야 한다.
- 사용자 정의 Role에 외부 ACP 연결용 `agent` 필드는 허용하지 않는다.
- 기존 외부 `search` Role과 내장 Role 설정 의미는 바꾸지 않는다.
- `AgentRoles()`와 `IsAgentRole()`은 내장 Role 판별 의미를 유지한다.
  설정 인스턴스에서 사용 가능한 native Role을 판별·나열하는 함수를 추가해
  `Validate`, `EffectiveAgent`, 모델 선택 UI 등 필요한 호출부에 적용한다.
- 새 이름은 소문자 영문으로 시작하고 소문자 영문·숫자·하이픈으로 구성한다.
- `default`, `embedding`, `search`와 내장 Role 이름은 예약어로 두어 모델 설정
  target 및 기존 Role과 충돌하지 않게 한다.
  길이는 1~64자로 제한한다. 등록되지 않은 이름을 기본 모델로 조용히 처리하지 않는다.

### 프로필: 작업 방식과 도구 구성

```yaml
version: 1
name: security-reviewer
description: 지정한 코드를 보안 관점에서 조사한다.
role: analyst
system_prompt: |
  사용자 요청에 해당하는 코드를 조사한다.
  구체적인 발생 조건과 근거가 있는 문제를 보고한다.
  각 발견 사항에 파일 위치와 수정 방향을 포함한다.
tools:
  - list_directory
  - read_file
  - run_command
  - wait
```

필수 필드는 `version`, `name`, `role`, `system_prompt`, `tools`다.
`description`은 선택 사항이다. `tools: []`는 도구 없는 실행을 의미하며,
필드 누락을 모든 도구 허용으로 해석하지 않는다.

프로필에는 모델 설정을 중복 저장하지 않는다. 같은 Role을 여러 프로필이
사용할 수 있고, 같은 프롬프트를 다른 Role에 연결한 프로필도 만들 수 있다.
출력 스키마와 종료 도구를 사용자가 설계하는 기능은 이번 범위에 넣지 않는다.

## 4. 저장과 로딩

프로필은 다음 디렉터리의 `*.yaml`, `*.yml` 파일로 관리한다.

- global: `~/.q/subagents/`
- workspace: `<workspace>/.q/subagents/`

프로필은 디렉터리 바로 아래 파일만 읽는다. 같은 이름이 두 범위에 있으면
workspace 프로필 전체가 global 프로필을 대체한다. 필드 단위 병합은 하지 않는다.
목록과 상세 조회에는 적용된 파일 경로와 범위를 표시한다.

같은 범위의 중복 이름은 오류다. YAML의 중복 키, 알 수 없는 필드, 지원하지 않는
버전, 빈 프롬프트, 잘못된 이름 및 도구 중복도 검증한다. 파일명보다 `name`이
프로필 식별자이며, 프로필 이름에도 Role과 같은 문자·길이 규칙을 적용한다.

global과 workspace 설정의 추가 병합 체계는 만들지 않는다. Role은 현재 활성
설정으로 해석한다. workspace 프로필을 다른 환경으로 옮겼을 때 Role이 없으면
필요한 Role 이름을 명시해 오류를 반환한다.

목록·조회·실행 요청마다 프로필을 다시 읽어 수동 편집을 반영한다. 실행 시작
후에는 프로필과 해석된 모델·도구 구성을 고정하고, 파일 변경은 다음 실행부터
적용한다. 잘못된 파일은 목록에 진단으로 표시하되 독립적인 정상 프로필의 실행을
막지 않는다. 충돌하거나 잘못된 workspace 정의에서 global 정의로 조용히 fallback하지 않는다.

TUI에서 새 프로필을 저장할 때는 global·workspace 범위를 선택하고 해당 디렉터리의
`<name>.yaml`에 저장한다. 기존 프로필 수정은 실제 원본 파일에 저장한다.
설정과 프로필 저장은 검증 후 atomic replace를 사용하고, 편집 시작 이후 원본이
외부에서 변경되었다면 덮어쓰지 않고 다시 읽도록 알린다. 저장 실패 시 편집 내용은
유지한다. Role 저장은 `/model`의 기존 config 저장 경로를 사용하고 다른 설정 필드를 보존한다.

## 5. 도구 제공

활성 세션 런타임에서 사용 가능한 도구를 이름으로 조회하고, 프로필의 `tools`에
지정한 것만 새 Runner에 제공한다. 내장 Role별 도구 필터를 적용하지 않는다.
프로필이 `scout` Role을 참조해도 모델 설정만 사용하며 ScoutRunner의 조사 계약은
따라오지 않는다.

- 이름은 런타임이 모델에 제공하는 정확한 도구 이름을 사용한다.
- 없는 도구 또는 현재 연결 상태에서 사용할 수 없는 도구는 실행 전에 오류로 알린다.
- 외부 MCP 도구는 현재 런타임에서 이미 사용 가능한 도구에 한해 선택한다.
  프로필에 연결 정보나 자격 증명을 추가하지 않는다.
- `submit_plan`, `submit_debug_report`, `review_task`, `delegate_scout`처럼 기존
  Runner가 주입하는 전용 도구는 일반 도구 목록으로 가져오지 않는다.
- `ask_to_user` 등 별도 인터랙션 처리가 필요한 도구도 첫 버전에서 추가하지 않는다.
- 명령 실행·파일 수정 등 각 도구의 기존 동작은 유지한다. 도구 선택 설정에
  새로운 읽기 전용 보장이나 권한 정책의 의미를 부여하지 않는다.

Runner의 실제 도구 호출도 선택된 도구 집합으로 전달한다. 모델이 제공받지 않은
이름을 호출하면 도구 오류로 처리한다. 이는 프로필의 실행 구성을 지키기 위한
동작이며 별도 권한 시스템을 도입하는 작업은 아니다.

## 6. 실행 계약

`subagent.CustomRunner`를 새로 추가한다. 기존 Griller/Planner/Coder/Review
Runner를 공통 Runner로 교체하지 않는다.

입력은 프로필 스냅샷, 해석된 `Spec`, 요청 문자열, 작업 디렉터리, 실행 ID,
선택된 도구 런타임 및 진행·기록 콜백이다.

실행 순서:

1. 프로필 로드와 정적 검증.
2. Role 및 모델 후보 해석, 사용 가능한 도구 검증.
3. 현재 세션의 취소 context 아래 독립된 메시지 목록과 실행 ID 생성.
4. 모델 호출과 도구 실행 반복.
5. 도구 호출 없이 비어 있지 않은 최종 assistant 응답이 나오면 성공 종료.
6. 결과를 부모 세션에 반환하고 실행 기록 확정.

메시지는 사용자 시스템 프롬프트, 최소한의 Q 실행 환경 정보, 실행 요청으로
구성한다. 기존 Griller 등 역할 전용 지침이나 일반 채팅의 전체 시스템 프롬프트를
자동으로 섞지 않는다. 실행 환경 정보는 작업 디렉터리, OS·셸, 도구 결과 처리 등
런타임 사용에 필요한 사실과 형식만 담는다.

첫 버전은 요청 문자열을 명시적인 입력 문맥으로 사용한다. 부모 대화 전체를
자동 복사하지 않는다. 모델 요청 시 현재 작업에 필요한 문맥을 요청에 포함하도록
도움말에 설명한다. 완료 응답은 부모 대화에 추가하지만 내부 도구 transcript는
부모 모델 문맥으로 그대로 복사하지 않는다.

새 Runner는 기존 모델 라우팅과 컨텍스트 축약을 사용하고, 일반 도구 결과의
Loom receipt 처리를 유지한다. 컨텍스트 축약 이후에도 프로필 프롬프트와 실행
요청을 유지해야 한다. 도구 오류는 모델에 반환해 수정 기회를 주고, 취소와
복구 불가능한 모델·기록 오류는 상위 실행으로 전달한다.

모델 반복 상한은 내부 기본값 320회로 제안한다. 이번에는 프로필 설정으로
노출하지 않는다. 빈 응답은 한 번 재요청하고 반복되면 실패 처리한다. 상한 도달은
성공으로 처리하지 않는다. 도구를 가진 마지막 호출 이후 최종 응답을 얻지 못한
경우에도 성공 보고서를 만들어내지 않는다.

## 7. TUI와 ACP 인터페이스

목록·상세 조회 및 실행 명령은 두 인터페이스에서 동일하게 제공한다.
인자 없는 `/subagents`는 TUI에서는 관리 화면을 열고 ACP에서는 목록을 반환한다.

```text
/subagents
/subagents list
/subagents show security-reviewer
/subagent security-reviewer 인증 처리 코드의 취약점을 조사해줘
```

| 명령 | 동작 |
| --- | --- |
| `/subagents` | TUI: 프로필 관리 화면 열기. ACP: `/subagents list`와 동일 |
| `/subagents list` | 적용 가능한 프로필의 이름·설명·Role·출처와 로딩 오류 표시 |
| `/subagents show <name>` | 프롬프트, 도구, Role, 적용 파일 표시 |
| `/subagent <name> <request>` | 선택한 프로필로 한 번 실행 |

별도의 `/subagents tools` 명령은 추가하지 않는다. 선택 가능한 도구의 이름과
설명은 TUI 프로필 편집 화면에서 조회하고 선택한다.

### TUI 관리 화면

`/subagents` 화면에 프로필과 Role 두 탭을 제공한다. 각 탭은 목록과 상세 영역,
생성·수정·삭제 동작을 제공한다. 생성·수정은 초안에서 진행하며 저장 전에
취소하면 원본을 바꾸지 않는다. 첫 버전에서 기존 항목의 이름은 식별자로 고정하고,
수정은 이름 외 설정에 적용한다.

기존 Q의 `frameStyle`, 제목·선택 강조·보조 설명·도움말 스타일을 사용한다.
프로필과 Role 모두 기존 관리 화면과 동일하게 `a add`, `e edit`, `d delete`를 사용하며
삭제는 두 번째 확인 입력 뒤에 실행한다. 탭에는 항목 수를, 목록에는 scope·모델 정책·
도구 상태의 요약을 표시한다.
Scope·Role은 직접 입력 대신 ←/→ 또는 Space로 순환하고 Enter로 목록을 연다.
프롬프트는 Tab으로 다음 필드, Shift+Tab·Esc·Ctrl+↑로 이전 필드로 이동하며 내용을
보존한다. Tools는 기본 도구와 연결된 외부 MCP 도구의 검색·복수 선택 목록을 제공한다.
저장된 프로필도 Scope를 변경할 수 있으며 대상에 같은 이름이 있으면 이동을 거절한다.
넓은 화면에서는 목록과 상세를 나란히, 좁은 화면에서는 위아래로 배치한다.
상세 영역의 긴 프롬프트·도구 설명·참조 목록은 PgUp/PgDn으로 독립적으로
스크롤한다. Role 편집 중에도 참조 프로필 목록을 표시한다.

프로필 탭:

- 생성: 이름, 설명, global·workspace 저장 범위, Role, 여러 줄 시스템 프롬프트,
  도구 목록을 입력한다. YAML을 직접 편집하지 않고 생성할 수 있어야 한다.
- Role은 내장 native Role과 등록된 커스텀 Role에서 선택한다. Role 탭에서 새
  Role을 저장하면 프로필 편집 초안을 유지한 채 선택 목록에 반영한다.
- 도구는 정확한 이름과 설명으로 검색하고 복수 선택한다. 빈 선택도 허용한다.
  기존 프로필의 현재 사용할 수 없는 도구는 표시하고 임의로 삭제하지 않는다.
- 수정: 기존 정의를 폼에 불러와 프롬프트·도구·Role·설명을 변경한다.
- 삭제: 선택한 원본 파일만 삭제한다. workspace 정의 삭제 시 같은 이름의 global
  정의가 다시 적용되면 그 결과를 표시한다. 실행 기록은 삭제하지 않는다.
- 관리 목록에서는 global·workspace 원본과 가려진 global 정의도 구분해 선택할 수
  있게 한다. 실행용 `/subagents list`는 적용된 정의를 중심으로 표시한다.

Role 탭:

- 생성: 커스텀 이름과 활성 모델 상속·명시적 모델·모델 그룹 중 하나를 선택하고
  추론 설정을 지정한다. 저장 위치는 기존 global config다.
- 수정: 커스텀 Role의 모델 선택과 추론 설정을 변경한다. 현재 workspace·global
  프로필 중 참조하는 항목을 함께 보여준다.
- 삭제: 커스텀 Role 등록을 제거한다. 현재 조회 가능한 global·workspace 프로필에
  참조가 있으면 해당 항목을 표시하고 Role을 먼저 바꾸도록 안내한다.
  다른 workspace까지 검색하지 않으며, 그곳의 누락된 Role은 실행 전 검증으로 알린다.
- 내장 Role은 선택과 조회가 가능하지만 이 화면의 삭제 대상이 아니다.
  내장 모델 설정의 기존 편집 경로는 유지한다.

파일 수동 편집과 같은 검증을 저장에도 적용한다. 프로필·Role 편집과 삭제는
다음 실행부터 반영하고 이미 시작한 실행은 스냅샷으로 계속한다.

이름 뒤 나머지 문자열 전체를 요청으로 사용한다. 이름이나 요청이 없으면
사용법을 반환한다. 별도의 입력 대기 모드는 첫 버전에 넣지 않는다.
프로필 이름별 slash command도 자동 생성하지 않는다.

TUI와 ACP는 명령 파서, 프로필 로더, 실행 서비스를 공유한다. TUI는 기존
진행 표시와 취소 동작에 연결하고, ACP는 command 목록과 세션 업데이트에
연결한다. ACP 호스트에 별도 승인 form이나 새 capability를 요구하지 않는다.
동일 세션에서는 기존 turn 실행 규칙을 따르며 추가 병렬 실행 관리자를 만들지 않는다.

실행 성공은 최종 텍스트, 실패는 구체적인 오류, 취소는 취소 상태로 반환한다.
실패·취소 후에도 입력 가능한 세션 상태로 복귀해야 한다. 기존 `/agents`와
`/debug`, `/plan`, `/review`의 등록 및 실행 분기는 유지한다.

## 8. 진행과 기록

기존 `ProgressEvent`, `TraceEvent`, lifecycle archive를 사용한다. 화면에서는
프로필 이름을 작업 주체로 표시하고, Role은 별도 메타데이터로 보존한다.
같은 Role을 쓰는 서로 다른 프로필을 이름과 실행 ID로 구분할 수 있어야 한다.

실행 기록에는 다음을 남긴다.

- 프로필 이름·원본 위치·실행 시점의 정의.
- Role과 실제 모델 후보 설정, 선택된 도구 이름.
- 요청, 시작·종료 시간, 성공·실패·취소 상태와 최종 결과 또는 오류.
- 기존 기반에서 지원하는 가시적 메시지와 도구 호출·결과 기록.

설정 전체나 연결 자격 증명은 복제하지 않는다. 새 plan checkpoint나 별도의
단계 복구 기능은 만들지 않는다. lifecycle 기반이 프로필 스냅샷을 저장할 수
없다면 커스텀 실행용 메타데이터 레코드를 추가한다. 기존 실행 기록 형식의
필수 필드와 기존 workflow 로그는 변경하지 않는다.

## 9. 구현 단계

### 단계 1: Role 해석 확장

- `config/config.go`에 등록된 native Role 조회·목록 함수를 추가한다.
- 사용자 정의 Role 검증과 `EffectiveAgent` 경로를 연결한다.
- `subagent.Resolve`의 모델 그룹·추론 검증을 그대로 재사용한다.
- `/model` 등 Role 나열 호출부를 조사해 필요한 화면에 등록된 Role을 표시한다.
- 내장 Role 판별을 도구 정책에 사용하는 호출부는 일괄 치환하지 않는다.

완료 기준: 등록한 새 Role로 `Spec`을 얻고, 미등록 Role은 실패하며, 기존 native
및 외부 Role 설정 테스트가 그대로 통과한다.

### 단계 2: 프로필 저장 형식과 로더

- 새 `subagent/profile.go`, `profile_store.go`에 정의·검증·파일 로딩을 구현한다.
- global·workspace 우선순위, 진단, 출처 정보, 실행 스냅샷을 구현한다.
- 프로필과 활성 설정의 Role 참조를 검증한다.
- 프로필 생성·수정·삭제 저장 API와 커스텀 Role 저장·삭제 서비스를 추가한다.
- 원본 범위 구분, atomic 저장, 외부 변경 충돌 및 Role 참조 검사를 구현한다.

완료 기준: 프로필을 파일로 작성·수정할 수 있고 다음 조회에 반영된다. 오류
파일과 이름 충돌을 숨기지 않으며 정상 프로필은 독립적으로 사용할 수 있다.

### 단계 3: 커스텀 Runner

- 새 `subagent/custom.go`에 독립된 모델·도구 루프를 추가한다.
- 프로필의 도구 선택 런타임과 완료·오류·취소 처리를 구현한다.
- 컨텍스트 관리, 모델 라우팅, Loom, 진행·실행 기록을 연결한다.
- 내장 Runner의 도구나 결과 계약을 수정하지 않는다.

완료 기준: 테스트용 모델로 도구 없는 응답, 여러 번의 도구 호출, 도구 오류
회복, 빈 응답, 반복 상한, 취소를 검증한다. 선택되지 않은 도구는 호출되지 않는다.

### 단계 4: 공통 앱 서비스와 TUI·ACP

- 새 `app/custom_subagent.go`에 공통 조회·실행 서비스를 추가한다.
- 공통 명령 파서를 두 인터페이스에 연결한다.
- slash completion, ACP command 목록, 도움말을 갱신한다.
- 부모 대화 결과 반영, 진행 표시, 취소 이후 상태 복구를 연결한다.
- `/subagents`에는 프로필 관리 화면을 추가하고 `/model`에는 커스텀 Role 생성·삭제를 추가한다.
- 여러 줄 프롬프트 편집, Role 선택, 도구 검색·복수 선택, 저장 범위 선택을 구현한다.
- 저장·삭제 후 목록 갱신, 편집 취소, 저장 오류 시 초안 유지를 연결한다.

완료 기준: 같은 프로필과 요청을 TUI·ACP에서 실행하면 같은 입력과 실행 계약을
사용한다. 목록·상세 조회와 관리 화면은 모델 호출 없이 처리된다.
TUI에서 파일 수동 편집 없이 `/model`로 커스텀 Role을 관리하고 `/subagents`로
프로필의 생성·수정·삭제를 마칠 수 있다.

### 단계 5: 회귀 검증과 사용 문서

- global·workspace 프로필 및 취소 동작을 TUI·ACP에서 각각 확인한다.
- TUI 생성·수정·삭제, 프롬프트 편집, 도구 선택 및 저장 실패 처리를 확인한다.

## 10. 검증 계획과 최종 완료 조건

자동 검증은 `config`, `subagent`, `app`의 해당 단위·통합 테스트를 중심으로
수행한다. 모델 응답은 fake client로 재현해 완료와 오류 전이를 검증한다.
기존 관련 테스트가 통과한 뒤 실제 설정으로 두 인터페이스의 기본 실행을 확인한다.

필수 시나리오:

- 기존 설정을 수정하지 않아도 모든 내장 기능이 이전과 동일하게 동작한다.
- 새 Role과 프로필을 파일로 작성해 TUI·ACP에서 실행한다.
- `/model`에서 새 Role을 생성·설정하고 `/subagents`에서 프로필을 생성·수정한 뒤 TUI·ACP에서 실행한다.
- `/subagents list`는 두 인터페이스에서 같은 적용 프로필 목록을 반환한다.
- `/subagents`에서 프로필을, `/model`에서 미참조 커스텀 Role을 삭제할 수 있다.
- 참조 중인 Role 삭제는 참조 목록을 표시하며, 내장 Role은 삭제하지 않는다.
- 편집 취소·저장 실패·외부 파일 변경 충돌 시 원본과 초안을 올바르게 보존한다.
- workspace 프로필 삭제 후 가려졌던 global 프로필이 다시 적용된다.
- 기존 native Role을 참조해도 내장 Runner 프롬프트·도구가 섞이지 않는다.
- workspace 프로필 우선순위와 중복·잘못된 파일 진단이 일치한다.
- 미등록 Role, 없는 모델·그룹, 사용할 수 없는 도구는 실행 전에 실패한다.
- `tools: []`는 도구 없는 요청을 만들고, 선택된 도구만 제공·호출된다.
- 실행 중 정의 파일을 바꿔도 진행 중인 실행에는 영향을 주지 않는다.
- 취소가 모델·도구 context로 전달되고 다음 요청을 받을 수 있다.
- 실행 기록에서 프로필·Role·결과를 구분할 수 있다.

완료 시 사용자는 세 가지 작업 설정인 시스템 프롬프트·도구 목록·Role만으로
커스텀 서브에이전트를 구성할 수 있어야 한다. 기존 워크플로 재구성이나 권한
체계 설계를 이 기능의 선행 조건으로 만들지 않는다.
