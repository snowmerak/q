# 모델별 출력 상한과 응답 복구

Studio의 **Settings → Models → Model behavior**에서 설정한다. 저장된 값은 다음
논리 생성부터 적용된다. 한 응답의 복구를 진행하는 중에는 해당 생성에서 선택한
모델·출력 상한·reasoning effort를 유지한다.

## 출력 상한

- **Maximum output tokens**: 한 API 요청에서 생성할 출력 토큰의 상한. 빈 값은
  Q의 상한 지정을 제거하고 요청 또는 제공자 기본값을 사용한다. 0은 허용하지 않는다.
- **Chat token parameter**: 기본 Standard는 `max_completion_tokens`, Legacy는
  `max_tokens`를 보낸다. Responses 모드에서는 `max_output_tokens`로 변환한다.
- **Allow missing finish reason**: 종료 사유를 생략하는 호환 서버에만 사용한다.
  일반 Q HTTP 클라이언트는 종료 사유를 요구한다.

요청에 더 작은 상한이 있으면 작은 값을 사용한다. 모델이 최대 출력량을 알려 준
경우 그 범위를 넘는 설정은 저장할 수 없다. 최대값을 알 수 없는 경우에는 제공자가
요청을 검증하며, 미지원 값은 오류로 표시된다.

이 값은 입력 가능한 컨텍스트 크기와 별개다. 추론 모델의 추론 토큰도 출력 상한을
소비한다. 전체 에이전트 작업이나 전체 대화의 비용 상한은 아니다.

같은 모델을 여러 역할·세션에서 사용하면 같은 모델별 상한을 적용한다. 폴백 그룹은
실제 선택된 후보 모델의 값을 사용한다. 상한 도달을 이유로 다른 후보를 자동 선택하지
않는다. 기존 네트워크/서버 실패 폴백은 유지한다.

현재 ChatGPT 구독·Codex 에이전트 연결은 공통 출력 상한을 지원하지 않아 입력을
비활성화한다. ACP에는 이 설정을 전송하지 않는다. ACP 서버의 자체 모델·reasoning
선택 기능은 기존대로 동작한다.

## 자동 복구

**Additional recovery attempts**는 최초 요청 이후 추가 생성 횟수다. 빈 값은 2회,
0은 자동 복구 비활성화이며 0~5를 설정할 수 있다. 출력 한도 복구와 빈 응답 복구는
한 카운터를 사용한다. 기존 429·5xx 등의 전송 재시도는 별도 설정이다.

| 중단 상황 | 처리 |
| --- | --- |
| 일반 텍스트의 출력 상한 도달 | 부분 답변을 유지하고 도구를 끈 상태에서 남은 답변을 이어받는다. |
| 잘린 툴 호출·혼합 출력 | 해당 생성의 툴 호출을 모두 보류하고 원래 정상 이력으로 한 번 전체 재생성한다. |
| 잘린 구조화 결과·압축 결과 | 한 번 더 간결한 완성본을 생성한다. 검증에 성공해야 적용한다. |
| 추론 토큰만 소진 | 같은 조건으로 반복하지 않고 상한·reasoning 설정 조정이 필요함을 표시한다. |
| 명확한 컨텍스트 부족 | 정상 이력으로 압축할 수 있는 경우 한 번 압축한 뒤 남은 복구 횟수 안에서 재시도한다. |
| 빈 응답 | 정해진 횟수 안에서 재시도한다. 정상 도구 이력을 임의로 삭제하지 않는다. |
| 필터링·거부·취소·기한 만료 | 재시도하지 않는다. 이미 받은 부분 결과를 보존한다. |
| ACP 등 서버가 도구를 실행하는 에이전트 | 미완료 결과와 사유를 남긴다. 프롬프트·세션·작업을 자동 재실행하지 않는다. |

복구는 출력 상한을 올리거나 reasoning effort를 낮추지 않는다. 정해진 횟수를
소진하거나 진전이 없으면 미완료 상태로 끝난다. 툴 인자나 JSON 조각을 이어 붙여
실행하지 않으며, 이미 완료한 도구·티켓·MR 작업을 답변 복구 때문에 반복하지 않는다.
`task_complete`를 수락한 뒤 마지막 응답만 잘린 경우에는 마지막 응답 수신만 복구한다.

자연어 이어받기의 문장 중복을 완벽하게 제거할 수는 없다. 문자열 일부를 추측해
삭제하지 않고 원래 조각과 생성 시도를 이력에 보존한다.

각 복구 요청도 토큰을 사용한다. 한 요청의 상한을 유지하더라도 **합산 비용은
늘어날 수 있다**. 제공자가 보고한 모든 시도의 사용량을 합산하며, 컨텍스트 추정은
합산 입력량 대신 마지막 실제 요청의 입력량을 사용한다.

## 이력과 진단

복구 중인 상태와 생성 시도는 세션의 실행 로그에 기록된다. 시도 ID·순번·종료 사유·
복구 방식·부분 텍스트·제안한 툴 호출·보고된 사용량을 확인할 수 있다. HTTP 인증
헤더나 원시 Responses 비공개 재생 데이터는 이 감사 이벤트에 포함하지 않는다.

잘린 제안·실패한 체크포인트는 실행 가능한 정상 이력으로 전달하지 않는다. 실패하거나
사용자가 중단한 부분 텍스트는 미완료 표시와 함께 대화 기록에 남기고, 다음 모델의
정상 컨텍스트에는 포함하지 않는다. Studio 새로고침은 저장된 실행 로그를 재생한다.
프로세스를 재시작했다고 감사 로그의 도구·원격 에이전트를 재실행하지 않는다.

모델이 보고한 reasoning 토큰은 생성 시도의 진단에 남긴다. 제공자가 사용량이나
reasoning 세부 수치를 보내지 않은 경우에는 값을 만들어 내지 않는다.

## 설정 파일

```yaml
model_output_limits:
  local/model: 16384
model_output_token_fields:
  local/model: max_tokens
model_allow_missing_finish_reason:
  local/model: true
generation_recovery:
  max_attempts: 2
```

Legacy 필드나 종료 사유 생략 호환이 필요 없으면 두 해당 설정을 생략한다. 추가
복구 횟수도 생략하면 2회다. 모델별 설정은 기존 Studio 내보내기/가져오기에 포함된다.

독립 Go 호스트의 주입 클라이언트는 `client.WithGenerationSettings`로 상한·추가 시도
횟수·종료 검사·`SafeReplay`를 명시할 수 있다. Q가 관리하는 연결은 제공자 종류로
재생성 가능 여부를 구분한다. 기존 주입 클라이언트는 종료 사유 생략 호환과 빈 응답
재시도를 유지하지만, `SafeReplay`를 명시하기 전에는 부분 생성의 재실행을 허용하지 않는다.

Q의 HTTP 클라이언트는 `SafeReplay=false`인 생성 요청의 전송 재시도도 비활성화한다.
Codex·ChatGPT 같은 원격 에이전트가 작업을 끝낸 뒤 응답만 유실된 경우를 구분할 수
없기 때문이다. 스트림 시작과 첫 청크 이전 재접속에도 같은 규칙을 적용한다.
모델 목록 조회와 임베딩 요청의 기존 전송 재시도 정책은 유지한다.

설계와 검증 범위는 [구현 계획](model-output-limit-recovery-plan.md)을 참고한다.
